## Descrição do PR (inglês)

```markdown
## Summary
- **Your data (Settings):** export everything to a versioned JSON file and import it back through the system file picker. Import is add-only: it never changes or removes what is already on the phone, shows a summary before writing, refuses invalid files as a whole, and is blocked during an active workout.
- **No more freezes with a large history:** history records are computed in one chronological pass and the presentation runs off the main thread. With ~208 workouts the debug APK used to freeze ~48 s at cold start and after an import (ANR when tapped); now the UI stays responsive with a loading state.
- **Robustness:** the command loop keeps processing user actions after a timed-out wait (a discard timeout used to silently drop every later edit).
- **Build on macOS/Linux and CI:** the PowerShell build and release scripts now also run on `pwsh` 7 on macOS and Linux (on Windows they still run on Windows PowerShell 5.1 and PowerShell 7; CI runs the release script under both), and a GitHub Actions workflow (`.github/workflows/ci.yml`) runs host tests, lint and the debug build on Linux (ubuntu) on every push and pull request, and the release script on Linux and Windows when `tools/`, `build.ps1`, `app/build.gradle.kts` or a workflow changes (and on every manual run). CI uses throwaway keys only: no secrets, no tags, no publishing.
- **Release script signer check changed (please review):** `tools/prepare-release.ps1` now reads the output of apksigner from build-tools 37 and newer, and fails closed: every certificate digest apksigner prints counts as a signer (except the source stamp), so an unknown signer format refuses the APK instead of being ignored. It still accepts only an APK signed solely by the original key; the default fingerprint, parameters and messages are unchanged. CI checks that two signers and a key rotation are refused, on build-tools 35 and 37, Linux and Windows.
- **Toolchain and database layer (please review):** Gradle 9.7, AGP 9.3 with built-in Kotlin, Kotlin 2.4, compileSdk 37 (targetSdk stays 35), current Compose and AndroidX libraries, and Room 2.8 with the system SQLite driver (`AndroidSQLiteDriver`). Migrations now use the `SQLiteConnection` API and are checked against reference dumps produced by the old code; on the emulator, an upgrade over the previous build kept the database contents (full SQL dump) and the preference files (byte for byte) identical, including an active workout and a running rest timer. The debug APK grows by about 1.9 MB.

No Room schema change (version 5), no DataStore key change, same applicationId and update.json contract.

## Verification
- Host: 482 unit/Robolectric tests, lint clean.
- Emulator (Pixel 8 API 35): see docs/superpowers/reports/2026-10-27-export-import-verificacao.md and 2026-10-27-pr-off-main-thread-verificacao.md.
- Not verified: physical phone, Google Drive/third-party file providers, TalkBack. Cold-start history still takes 15–20 s on the debug APK (2.3–3.1 s on an R8 build) — tracked in the ROADMAP.
```

## Release (depois do merge no repositório original)

Pelo roteiro de [AGENTS.md](../../../AGENTS.md#releases) e [UPDATES.md](../../../UPDATES.md):

1. **Chave de assinatura (bloqueante).** O APK precisa sair assinado com a chave debug original, que está com o dono de `ReiTut/Mooscles`. Um build feito no Mac do fork tem outra chave e não atualiza nenhuma instalação existente. Guardar uma cópia da chave no 1Password, cofre **Agentes**, é item da fase 0 do ROADMAP. Nunca gerar outra chave, nunca pedir a ninguém para desinstalar o app e nunca publicar um APK assinado com a chave do Mac.
2. Em `app/build.gradle.kts`, subir `versionCode` para **≥ 18** (o upstream já publicou a v1.4.6 com `versionCode` 17) e `versionName` de "1.4.5" para **"1.5.0"**.
3. Em `build.ps1`, mudar `-PreviousVersionCode` para **17** (último código distribuído, da v1.4.6 do upstream; esquecer isso faz o `prepare-release.ps1` aceitar um `versionCode` que não é novo).
   - **Decisão do usuário (2026-10-27): o fork fica separado e não integra mudanças do original até o PR final.** A v1.4.6 do `ReiTut/Mooscles` (commit 047842a) refez por conta própria a análise de PR e os editores do treino. 4. O `prepare-release.ps1` agora lê a saída do apksigner das build-tools 37 ou mais novas, então a release funciona em máquinas com build-tools recentes (antes só a 35 passava). Ver o [relatório](../reports/2026-10-27-macos-build-ci-verificacao.md).

## Pendências conhecidas que não bloqueiam o PR

- **Fase 1A** ([verificação](../reports/2026-10-27-phase1a-verificacao.md)):
  - o APK debug cresceu 1,78 MiB (19,9 → 21,8 MB), acima do orçamento de ~1 MB da spec. Aceito com o número corrigido (`androidx.window` via Compose UI 1.12, necessário para a fase 3);
  - o indicador da barra de navegação inferior ficou mais estreito (64 → 56 dp), por causa do Material 3 novo. É a única diferença visual encontrada entre antes e depois no emulador;
  - o Room agora executa `PRAGMA synchronous = NORMAL` e `busy_timeout` nas conexões que configura. No emulador Android 15 o framework já usava `NORMAL`; em aparelhos cujo framework usa `FULL` com WAL, uma queda de energia pode perder a última transação confirmada. Copiar para o `VERIFICATION.md` na release;
  - nada foi testado em Android 16 nem em celular físico.
- O histórico aparece 15–20 s depois de abrir o APK debug, e a meta era 3 s. Dois acompanhamentos estão no ROADMAP: medir no aparelho e distribuir um build não debuggable assinado com a chave original.
- As medições no emulador foram feitas com renderização por software. A GPU do host foi ligada só depois, então os números de quadros são pessimistas.
- Minors estacionados na revisão do loop de comandos:
  - backup e export tratam um cancelamento vazado como erro global;
  - um timeout no descarte pula `onTrainingChanged`;
  - `initialize()` ainda relança cancelamentos;
  - cancelamentos vazados não vão para o log.
- `DiscardNavigationHostTest` falhou uma vez numa execução completa local, com `AppNotIdleException` ("Compose did not get idle after 1 attempts in 60 SECONDS") em `loadingDoesNotAllowFooterActionsBeforeNavigationIsReady`, e passou ao rodar de novo. A causa no código não foi encontrada: o teste não tem laço de recomposição (as animações infinitas são canceladas pelo próprio Compose Test e cada passada de espera é limitada), leva 0,3 s na suíte e não falhou em 10 execuções seguidas da classe, nem em 5 com a CPU saturada (14 processos `yes` em 10 núcleos). O "1 attempts" mostra que uma única passada passou dos 60 s, o que indica a JVM de teste parada (CPU disputada com o emulador, ou GC no heap padrão de 512 MiB). A suíte agora roda em forks paralelos com 1 GiB cada, o que reduz esse risco sem mexer no teste; se voltar a falhar, guardar o XML completo do resultado.
- Corrigidos em `test: fix two flaky host tests`: `AppViewModelBackupHostTest.invalidFileShowsReasonAndKeepsData` (esperava "uma mensagem" e podia pegar a anterior antes de a limpeza ser publicada) e `AppViewModelFoldersDiscardHostTest:135` (contava os alarmes logo ao ver o timer "rodando", antes de o `RestTimerController` registrar o alarme).
