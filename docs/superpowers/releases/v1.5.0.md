O dono do repositório original deve aceitar tudo isso de forma explícita, e a mudança no script de release em especial, porque é ela que protege a chave. Se preferir, esses commits viram um PR separado.

## Descrição do PR (inglês)

```markdown
## Summary
- **Your data (Settings):** export everything to a versioned JSON file and import it back through the system file picker. Import is add-only: it never changes or removes what is already on the phone, shows a summary before writing, refuses invalid files as a whole, and is blocked during an active workout.
- **No more freezes with a large history:** history records are computed in one chronological pass and the presentation runs off the main thread. With ~208 workouts the debug APK used to freeze ~48 s at cold start and after an import (ANR when tapped); now the UI stays responsive with a loading state.
- **Robustness:** the command loop keeps processing user actions after a timed-out wait (a discard timeout used to silently drop every later edit).
- **Build on macOS/Linux and CI:** the PowerShell build and release scripts now also run on `pwsh` 7 on macOS and Linux (on Windows they still run on Windows PowerShell 5.1 and PowerShell 7; CI runs the release script under both), and a GitHub Actions workflow (`.github/workflows/ci.yml`) runs host tests, lint, the debug build and the release script on Linux and Windows. CI uses throwaway keys only: no secrets, no tags, no publishing.
- **Release script signer check changed (please review):** `tools/prepare-release.ps1` now reads the output of apksigner from build-tools 37 and newer, and fails closed: every certificate digest apksigner prints counts as a signer (except the source stamp), so an unknown signer format refuses the APK instead of being ignored. It still accepts only an APK signed solely by the original key; the default fingerprint, parameters and messages are unchanged. CI checks that two signers and a key rotation are refused, on build-tools 35 and 37, Linux and Windows.

No Room schema change (version 5), no DataStore key change, same applicationId and update.json contract.
```

## Release (depois do merge no repositório original)

Pelo roteiro de [AGENTS.md](../../../AGENTS.md#releases) e [UPDATES.md](../../../UPDATES.md):

1. **Chave de assinatura (bloqueante).** O APK precisa sair assinado com a chave debug original, que está com o dono de `ReiTut/Mooscles`. Um build feito no Mac do fork tem outra chave e não atualiza nenhuma instalação existente. Guardar uma cópia da chave no 1Password, cofre **Agentes**, é item da fase 0 do ROADMAP. Nunca gerar outra chave, nunca pedir a ninguém para desinstalar o app e nunca publicar um APK assinado com a chave do Mac.
2. Em `app/build.gradle.kts`, subir `versionCode` de 16 para **17** e `versionName` de "1.4.5" para **"1.5.0"**.
3. Em `build.ps1`, mudar `-PreviousVersionCode` de 15 para **16** (hoje está em 15 e o último código distribuído é 16; esquecer isso faz o `prepare-release.ps1` aceitar um `versionCode` que não é novo).
4. O `prepare-release.ps1` agora lê a saída do apksigner das build-tools 37 ou mais novas, então a release funciona em máquinas com build-tools recentes (antes só a 35 passava). Ver o [relatório](../reports/2026-10-27-macos-build-ci-verificacao.md).
5. Atualizar o `README.md` (a seção da versão atual e a de Download) e o `VERIFICATION.md`, este com o que foi testado e o que **não** foi: copiar as listas de "não verificado" dos dois relatórios.
6. Fazer o commit, criar a tag `v1.5.0`, publicar sem force e rodar `tools/publish-release.ps1 -NotesFile docs/superpowers/releases/v1.5.0.md`. O script cria um rascunho; só usar `-Publish` depois de revisar.
7. Marcar a fase 0 no ROADMAP com o link da release.

## Pendências conhecidas que não bloqueiam o PR

- O histórico aparece 15–20 s depois de abrir o APK debug, e a meta era 3 s. Dois acompanhamentos estão no ROADMAP: medir no aparelho e distribuir um build não debuggable assinado com a chave original.
- As medições no emulador foram feitas com renderização por software. A GPU do host foi ligada só depois, então os números de quadros são pessimistas.
- Minors estacionados na revisão do loop de comandos:
  - backup e export tratam um cancelamento vazado como erro global;
  - um timeout no descarte pula `onTrainingChanged`;
  - `initialize()` ainda relança cancelamentos;
  - cancelamentos vazados não vão para o log;
  - há um flake antigo em `AppViewModelFoldersDiscardHostTest:135`.
- Flake em `AppViewModelBackupHostTest.invalidFileShowsReasonAndKeepsData:260`, visto no CI (run 40591041005, tentativa 1): depois de `clearBackupMessage()` e de um novo `prepareImport`, o `awaitUi { !busy && message != null }` pode aceitar a mensagem antiga ("This file is not a Mooscles backup.") antes de a limpeza ser publicada, e o `startsWith("This backup contains invalid data:")` falha. A correção é só no teste: esperar `message == null` depois da limpeza, como o `idleCommands` já faz.
